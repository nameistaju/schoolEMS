Telugu Pickles — System Design

An e-commerce store for authentic Indian veg and non-veg pickles, built as a cloud-native microservice system to demonstrate the full DevOps journey: run locally → push to Amazon ECR → provision Amazon EKS with Terraform → continuous delivery with Argo CD → AIOps with Amazon Bedrock.

Version 1.0Region us-east-1Node.js 22 · React 18 · PostgreSQL 16EKS 1.34 · Argo CD · Prometheus · Grafana

Summary

What was built and why it is shaped this way.

7container images
6Node.js microservices
36pickles (20 veg · 16 non-veg)
5databases, one per stateful service
1public entry point (nginx → gateway)

Telugu Pickles replaces the earlier "boutique" demo. Shoppers browse Andhra, Telangana and pan-Indian pickles (Avakaya, Gongura, Magaya, Natu Kodi, Gongura Mutton, Royyala, Peethala…), filter by veg / non-veg, region and spice level, add 250 g / 500 g / 1 kg packs to a cart, and check out with UPI, card or cash on delivery (payments are simulated).

Design goals

  • Realistic enough to be worth operating: auth, catalogue, cart, orders, payments, stock.
  • One image runs unchanged on a laptop and on EKS (config only through env vars).
  • Self-bootstrapping: no init scripts, restore jobs or manual SQL.
  • Observable by design: JSON logs with request IDs, RED + business metrics.
  • Controllable failure: fault-injection switches for the AIOps demo.

Delivery path

  1. Local: docker compose up → 10 containers.
  2. ECR: 7 repositories (Terraform) + image push.
  3. EKS: VPC, cluster, nodes, EBS CSI, Argo CD, monitoring (Terraform).
  4. CD: GitHub Actions bumps tags in gitops/; Argo CD syncs.
  5. AIOps: Bedrock agent "Kira" reads logs, metrics and cluster health.

How the application communicates

Synchronous REST over Kubernetes DNS, authenticated with JWTs and traced with a request ID.

North–south (browser → system)

  1. Browser loads the SPA from nginx and calls relative URLs like /api/products. No API host is baked into the bundle.
  2. nginx proxies /api/ to ${GATEWAY_URL} (env-substituted at container start).
  3. Gateway matches the prefix, strips /api and forwards: /api/cart/items → cart-service:4003/cart/items.
  4. Upstream down? Gateway answers a friendly JSON 503 and counts tp_dependency_errors_total.

East–west (service → service)

  1. Discovery is plain DNS: http://catalog-service:4002 (Compose network or Kubernetes Service).
  2. A shared callService() client adds a 5 s timeout, forwards Authorization and X-Request-Id, and maps upstream 5xx to 502/503.
  3. Internal-only routes live under /internal/* and are never routed by the gateway.
  4. Every hop logs one JSON line carrying the same requestId, so one checkout can be traced across 4 services.

Authentication flow

auth-service signs a JWT (sub = user id, issuer telugu-pickles-auth) with JWT_SECRET. cart and order services verify it locally with the same secret via requireAuth, so no auth round-trip per request. When order-service calls cart-service it forwards the caller's token, so the cart is always read as that user.

Checkout saga

order-service coordinates four steps across three services. A failure after stock is reserved triggers a compensating action, so inventory never leaks.

Why a saga and not a distributed transaction?Each service owns its own database, so one ACID transaction across them is impossible. The saga keeps every step locally atomic and undoes earlier steps explicitly. Idempotency keys and an outbox are the next hardening steps for production.

Data design

Database-per-service on one PostgreSQL server. No service ever reads another service's tables.

Self-bootstrapping databases

On start-up each service (in common/db.js):

  1. retries the connection with back-off until Postgres is ready;
  2. runs CREATE DATABASE for its own DB if missing (tolerates the race between replicas);
  3. takes a pg_advisory_lock and runs idempotent migrations;
  4. seeds data with UPSERTs (catalogue + demo user) — safe on every restart.

This removes the boutique project's fragile init-script / restore-job dance (and its lost+found confusion). A fresh EBS volume just works.

Pricing rules (single source: common/pricing.js)

Catalogue stores the 500 g price in whole rupees. 250 g = ×0.55, 1 kg = ×1.9 (rounded). Free shipping at ₹999, otherwise ₹79. Prices shown in the browser are for display only; cart and order totals are always recomputed on the server.

Notable choices

  • Every jar is a generated SVG: pickle colour, cloth lid (green = veg, red = non-veg) and a Telugu label. Zero image assets or licensing issues.
  • Guests can fill a cart in localStorage; on login it is merged server-side via POST /api/cart/merge.
  • FSSAI-style veg / non-veg marks, spice meter in chillies, Telugu names in Noto Sans Telugu.
  • Responsive down to phone width; tested with headless Chrome screenshots.

Capacity sizing (why 2 nodes)

m7i-flex.large supports at most 29 pods (VPC CNI ENI limit). Expected pods: app 10 (frontend ×2, gateway ×2, catalog ×2, 4 others) + Postgres 1, Argo CD ≈ 7, monitoring ≈ 7, kube-system ≈ 11 (aws-node, kube-proxy, CoreDNS, EBS CSI, metrics-server) → ≈ 36. One node would hit the "too many pods" error the earlier t3.medium cluster ran into, so desired = min = 2, max = 3.

ResourcesRequests 50m CPU / 96 Mi, memory limit 256 Mi per service (no CPU limit to avoid throttling); Postgres 100m / 256–512 Mi.

ExposureOnly Service/frontend is type: LoadBalancer; everything else is ClusterIP.

CI/CD & GitOps

GitHub Actions (.github/workflows/ci.yml)

  • Path-filtered trigger + workflow_dispatch.
  • Supports GitHub OIDC (AWS_ROLE_ARN, no long-lived keys) or access-key secrets.
  • Immutable tags = commit SHA, so a deployment maps 1:1 to a commit.
  • Fixes the boutique bug where sed searched for the real account ID while manifests held a placeholder, so tags never changed.

Argo CD Application (created by Terraform, modules/platform)

  • Watches main / gitops/; automated: {prune, selfHeal}.
  • ServerSideApply for the large Grafana dashboard ConfigMap.
  • Retry with back-off; finalizer cleans up on delete.
  • Rollback = git revert of the bot commit (or Argo CD history).

Observability

Metrics

RED: http_requests_total, http_request_duration_seconds (route templates, low cardinality), http_requests_in_flight.

Business: tp_orders_placed_total{status}, tp_order_value_rupees_total, tp_payments_total{method,result}, tp_dependency_errors_total{dependency}.

Runtime: Node.js heap, event-loop lag, CPU. Every series carries app=<service>.

Logs

One JSON object per line on stdout / stderr: ts, level, service, msg, requestId, …. On EKS, Fluent Bit ships them to CloudWatch log group /eks/telugu-pickles/pods, which is queryable with Logs Insights and readable by Kira.

Alerts: HighServerErrorRate (>5 %), CheckoutPaymentFailures, SlowRequestsP95 (>1 s), PodRestartingOften.

Security

In place

  • bcrypt password hashes; signed, expiring JWTs; same error for unknown email and wrong password.
  • Server-side pricing & stock checks; parameterised SQL everywhere.
  • Internal APIs (stock, payments) unreachable from the internet.
  • Login / register rate limiting; security headers; request size limit (100 KB).
  • Non-root, read-only, capability-free containers; Pod Security admission.
  • ECR scan on push; encrypted EBS and ECR.
  • JWT_SECRET required when NODE_ENV=production.

Highlights

🫙 Real domain

36 regional pickles with Telugu names, pack sizes, spice levels, stock and a working checkout.

🔁 Build once, run anywhere

Same 7 images locally and on EKS; relative /api + nginx templating; config only via env.

🧱 Zero-touch data

Services create their own DBs, migrate under an advisory lock, and seed idempotently.

↩️ Saga with compensation

Checkout never leaks stock when payment fails, and this was proven with an injected failure.

🔍 Traceable

JSON logs + request IDs across hops + RED and business metrics + ready-made dashboard and alerts.

🧪 Built-in chaos

Four environment knobs create realistic incidents for the Bedrock agent to diagnose.

🚀 Loop-safe GitOps

Kustomize image overrides + path-filtered CI + Argo CD auto-sync / self-heal.

🛡️ Hardened pods

Non-root, read-only FS, dropped capabilities, probes, rolling updates with no downtime.

✅ Tested

7 unit tests in CI and a 25-step smoke test reusable against the EKS URL.

Runbook: zero to demo

Full student walkthrough with screenshots-worth of detail: docs/CICD-EKS-GUIDE.md. Local only: projects/telugu-pickles/LOCAL-SETUP.md.

  1. Run locally 
    cd projects/telugu-pickles
docker compose up -d --build && ./scripts/smoke-test.sh      # 25 passed
  2. Bootstrap (laptop, once): S3 state bucket + GitHub OIDC role (+ Route 53 zone when a domain is set) 
    cd projects/Infrastructure/bootstrap
terraform init && terraform apply
terraform output github_actions_role_arn
  3. GitHub: Settings → Secrets and variables → Actions → secret AWS_ROLE_ARN = the role ARN. That is the only secret.
  4. git push → Infrastructure workflow: Gitleaks + Trivy → terraform plan → terraform apply (VPC, EKS 1.35, ECR, Argo CD, kube-prometheus-stack, AWS Load Balancer Controller, Fluent Bit → CloudWatch, app Secret, Argo CD Application) ≈ 30 min.
  5. App CI (runs on app changes, or Run workflow): tests → build 7 images → Trivy image gate → push :<git-sha> to ECR → bot commits tags to gitops/kustomization.yml.
  6. Argo CD syncs within ~60 s: 
    aws eks update-kubeconfig --name telugu-pickles-eks --region us-east-1
kubectl -n argocd get application telugu-pickles          # Synced / Healthy
kubectl -n telugu-pickles get ingress frontend            # ADDRESS = shop URL (http://)
kubectl -n argocd port-forward svc/argocd-server 8081:80
kubectl -n monitoring port-forward svc/kube-prometheus-stack-grafana 3001:80
  7. CloudWatch: aws logs tail /eks/telugu-pickles/pods --follow; alarm telugu-pickles-error-spike on metric TeluguPickles/AppErrorCount.
  8. Domain (optional): set domain_name in bootstrap → GoDaddy nameservers → set domain_name in terraform.tfvars → push → https://shop./argocd./grafana.<domain> (ACM + ExternalDNS).
  9. AIOps: setup-iam.sh → create 3 Lambdas → set PROMETHEUS_URL → deploy.sh → streamlit run app.py, then run the scenarios in section 14.
  10. Tear down: Actions → Infrastructure → Run workflow → destroy (confirm "destroy"). It runs scripts/pre-destroy.sh first so the ALB and EBS volume are not orphaned.
