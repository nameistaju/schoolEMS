  3. Open it.

    URLWhatLogin
    http://localhost:3000The shopdemo@telugupickles.in / Pickle@123
    http://localhost:8080/api/healthHealth of every service (JSON)—
    http://localhost:9090Prometheus—
    http://localhost:3001Grafanaadmin / admin

  4. Run the 25-check smoke test. It browses, logs in, adds to the cart, orders, checks stock, then cancels.

    Git Bash
    ./scripts/smoke-test.sh          # expect: Result: 25 passed, 0 failed

The services read four fault settings: PAYMENT_DECLINE_RATE, PAYMENT_LATENCY_MS, CHAOS_ERROR_RATE and CHAOS_LATENCY_MS. In the cloud they live in gitops/k8s/platform/config.yml. Later, in stop 14, you'll use them to give Dude something to investigate.

Prepare AWS and check Bedrock

Laptop + AWS console10 min

  1. Get an IAM user with administrator rights, with an access key, from your instructor or your own account. In the console: IAM → Users → Create user, attach AdministratorAccess, then Security credentials → Create access key → CLI.

  2. Log in from the CLI, with region us-east-1. Everything in this project runs there, because it has the widest Bedrock model coverage.

    Git Bash
    aws configure                     # key, secret, region: us-east-1, output: json
aws sts get-caller-identity       # copy the "Arn" — you need it in stop 4
aws configure get region          # must print us-east-1

  3. Check that Bedrock answers for Amazon Nova. Nova works without any approval form. Each test costs a fraction of a cent.

    Git Bash
    aws bedrock-runtime converse --region us-east-1 \
  --model-id us.amazon.nova-pro-v1:0 \
  --messages '[{"role":"user","content":[{"text":"Say hello in Telugu"}]}]' \
  --inference-config maxTokens=50

aws bedrock-runtime converse --region us-east-1 \
  --model-id us.amazon.nova-lite-v1:0 \
  --messages '[{"role":"user","content":[{"text":"hi"}]}]' \
  --inference-config maxTokens=20

    A JSON reply with "output" and "usage" means you're ready. AccessDeniedException means your user lacks Bedrock permissions, or the account has a block on Bedrock. Ask your instructor.

Region trap

If your CLI default region is something else, such as ap-south-2, commands like aws lambda invoke look in the wrong region and say the function doesn't exist. Either set the default to us-east-1 or add --region us-east-1 to every command, as this guide does.

Why the model IDs start with us.

us.amazon.nova-pro-v1:0 is a cross-region inference profile. Bedrock can serve your call from us-east-1, us-east-2 or us-west-2, whichever has capacity. You get fewer throttling errors, and the price is the same. The model is still Amazon Nova Pro.

Add the one GitHub secret

GitHub3 min

  1. Fork → Settings → Secrets and variables → Actions → New repository secret. Set name AWS_ROLE_ARN and value = github_actions_role_arn from stop 5.

  2. Settings → Actions → General → Workflow permissions → Read and write permissions. The CI bot commits new image tags.

  3. Settings → Environments → production appears after the first run. Add yourself as a required reviewer, so promote, abort and destroy wait for your click.

Where the other passwords are

Nowhere in GitHub. Terraform generates the database, JWT and Grafana passwords, keeps them in the encrypted S3 state and puts them in Kubernetes Secrets. The CI bot's push token is GitHub's built-in GITHUB_TOKEN.

Test a canary that fails and rolls back by itself

This is the incident Dude will explain in stop 14. Add a chaos variable to the catalog container's env: in gitops/k8s/apps/catalog-service.yml:

YAML (inside the container env list)
            - name: CHAOS_ERROR_RATE
              value: "0.5"        # new pods fail 50% of requests

Commit and push. It's a Git-only change, so no CI build runs. After the 1-minute pause the analysis measures about 50% errors on the canary pod. The Rollout becomes Degraded (RolloutAborted: Metric "canary-5xx-ratio" assessed Failed), and traffic returns to the old pods. To clean up, remove the two lines, commit and push.

Meet Dude: AIOps on Bedrock with Nova

Lambda + Bedrock15 min read

Dude is an AI site-reliability engineer. When you ask a question, or when the error alarm fires, he sends three specialist agents to collect evidence. Then he writes one report: summary, impact, root cause, evidence, recommended actions and prevention. He is read-only: he recommends and never changes anything.

What Amazon Bedrock is, in one paragraph

Bedrock is AWS's service for calling foundation models, such as Amazon Nova, Anthropic Claude and Meta Llama, through one API. You don't run any servers or GPUs, and you don't create a "model resource". You call the model ID and pay per token. That's why Terraform creates no Bedrock resources for Dude. It only gives the Lambda's IAM role permission to invoke the two model IDs.

How one agent works: the Converse tool-use loop

Every agent, Dude included, runs the same ~40-line loop in projects/aiops-assistant/lambda/kira.py (run_agent):

  1. Send the conversation and the list of tools to the model with bedrock.converse().
  2. If the model replies stopReason: "tool_use", run the requested tools in parallel and append their results.
  3. Repeat, up to 6 turns, until the model answers in plain text.
Python: the heart of kira.py
bedrock = boto3.client("bedrock-runtime", region_name=REGION,
                       config=Config(retries={"max_attempts": 5, "mode": "adaptive"}, read_timeout=120))

resp = bedrock.converse(
    modelId=model,                         # us.amazon.nova-pro-v1:0 for Dude, nova-lite for agents
    system=[{"text": system}],             # the agent's instructions
    messages=messages,                     # conversation so far, including tool results
    toolConfig={"tools": tools},           # JSON schemas of the tools it may call
    inferenceConfig={"maxTokens": max_tokens},   # always explicit: 3000 Dude, 1500 agents
)
usage = resp["usage"]                      # inputTokens / outputTokens: what you pay for

Why not "Bedrock Agents"?

Classic Bedrock Agents is in maintenance mode and closed to new accounts. CreateAgent returns AccessDenied. The Converse loop does the same job in code you can read, which is better for learning. AWS's managed next step for hosted agents is Bedrock AgentCore.

Break it on purpose and let Dude explain

Full AIOps drill20–25 min

Pick one of the three drills. Run the traffic loop from stop 10 during all of them.

Drill 1: test the alarm path without breaking anything

Git Bash
aws cloudwatch set-alarm-state --region us-east-1 --alarm-name telugu-pickles-error-spike \
  --state-value ALARM --state-reason "Manual test of the AIOps pipeline"
aws logs tail /aws/lambda/telugu-pickles-kira --region us-east-1 --follow     # report appears in ~1 min

Drill 2: payments start failing

  1. In gitops/k8s/platform/config.yml set PAYMENT_DECLINE_RATE: "0.8", then commit and push.

  2. Argo CD updates the ConfigMap. Restart the payment pods so they read the new value:

    Git Bash
    kubectl -n telugu-pickles rollout restart deploy payment-service
cd projects/telugu-pickles && for i in 1 2 3 4; do ./scripts/smoke-test.sh "http://$ALB"; done

  3. Watch the evidence pile up: Grafana's payment panel, the CheckoutPaymentFailures alert, ERROR lines in CloudWatch, and the alarm going to ALARM.

  4. Ask Dude: "Are payments failing? Since when, and how many orders were affected?" Also check the automatic report in the Lambda log.

  5. Set it back to "0", push, and restart payment-service again.

Drill 3: a bad canary, an automatic rollback, an automatic report

  1. Add CHAOS_ERROR_RATE: "0.5" to catalog-service, as in stop 11, then push.

  2. Argo Rollouts sees more than 5% errors on the canary pod and aborts. Traffic goes back to the stable pods.

  3. The canary's ERROR logs push the CloudWatch alarm over 5 errors in 5 minutes. SNS invokes Dude.

  4. About a minute later the report is in /aws/lambda/telugu-pickles-kira, and in your email if you set one. It should name the canary, the failed analysis and the 503 chaos log lines, and recommend a git revert.

  5. Ask in the chat: "Why did the last catalog-service canary roll back?" Then remove the env lines and push.

What to point out to the class

No human looked at a dashboard. Argo Rollouts protected the shoppers with a metric check. The alarm woke the AI, the AI collected evidence from logs, metrics and Kubernetes, and a human gets a root-cause report to act on. That's AIOps.

Option A: from GitHub

Actions → Infrastructure → Run workflow, choose destroy, type destroy in the confirm box, then approve production.

Option B: from your laptop

Git Bash, from the repo root
cd projects/Infrastructure
ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
terraform init -backend-config="bucket=telugu-pickles-tfstate-$ACCOUNT"
../../scripts/pre-destroy.sh telugu-pickles-eks us-east-1    # removes the ALB + database volume first
terraform destroy                                            # yes; about 15 min

pre-destroy.sh matters because Kubernetes controllers create the load balancer and the database disk, not Terraform. If they're left behind, they block the VPC deletion and keep costing money.

If destroy hangs or fails the first time

Common causes: namespace deletion times out because pods are stuck Terminating, or DependencyViolation on the internet gateway. Force-delete the stuck pods and run destroy again:

Git Bash
for ns in argocd monitoring amazon-cloudwatch telugu-pickles; do
  kubectl delete pods --all -n $ns --force --grace-period=0
done
terraform destroy

The gateway error clears once the nodes are gone.

Git Bash: prove it's gone
aws eks list-clusters --region us-east-1                          # []
aws ec2 describe-instances --region us-east-1 --filters Name=instance-state-name,Values=running \
  --query 'Reservations[].Instances[].InstanceId'                  # []
aws elbv2 describe-load-balancers --region us-east-1 --query 'LoadBalancers[].LoadBalancerName'   # []
terraform state list | wc -l                                       # 0

What stays (almost free): the bootstrap S3 bucket, the GitHub OIDC role and the AWS_ROLE_ARN secret. Rebuild later by re-running the Infrastructure workflow or a laptop terraform apply, then App CI.
